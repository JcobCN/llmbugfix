# LLM Bug 自动修复系统 —— 全流程说明

> 面向：管理者与测试人员。说明从"测试人员报告一个 Bug"到"系统自动产出修复并推送"的完整过程。

---

## 一句话概括

测试人员在网页上**像聊天一样描述 Bug**，系统通过 AI 对话补齐信息、生成规范报告，确认提交后**自动克隆代码仓库、让 AI 修复工程师定位并修改代码、AI 评审员把关**，最终产出可推送的修复补丁（DRY_RUN 模式下仅保存产物，不推送）。

---

## 各阶段详解

### ① AI 接访对话（测试人员主要操作界面）

- 打开系统首页，直接用自然语言描述问题：**做了什么、实际发生什么、期望结果**
- AI 接访员每轮最多追问 3 个问题，典型追问：复现步骤、控制台报错、环境版本、**代码仓库地址**（首次报告某项目时）
- 页面右侧实时同步一份 **Markdown 格式的 Bug 报告**，可直接编辑；人工改过的字段优先级高于 AI
- 页面实时显示**完整度评分**（0-100）

**测试人员须知：**

| 要点 | 说明 |
|---|---|
| 评分 ≥ 65 才能提交 | 缺关键信息时系统会继续追问 |
| 回答 "unknown" 是合法的 | 不知道就答不知道，系统不会无限追问 |
| 不要粘贴密码 / Token | 对话内容会进入报告和日志 |
| 仓库地址用 Git remote URL | 如 `http://.../xxx.git`，不要给本地路径 |

### ② 确认提交

- AI 展示整理好的报告摘要，测试人员**显式确认后**才会提交（不会误提交）
- 提交后生成唯一编号，如 `BUG-000004`

### ③ 分诊（自动）

- 信息充分（score ≥ 65）→ `QUEUED`，进入修复队列
- 信息不足 → `NEEDS_INFO`，不消耗修复资源

### ④ 准备环境（自动）

- 按报告里的仓库地址克隆代码（同一仓库只克隆一次，之后复用）
- 为每个 Bug 创建**独立的工作区**（git worktree + 独立分支 `ai/BUG-编号-title`），互不干扰

### ⑤ AI 修复（自动，核心环节）

- AI 修复工程师（Fixer）在工作区内自主工作：阅读代码 → 搜索定位 → 分析根因 → 修改代码 → 自述报告
- 可使用的工具：读文件、搜索、编辑、写文件、执行命令
- 输出必须是结构化 JSON 报告（根因、改动文件、信心值等）。格式不对时系统会**自动把错误信息反馈给 AI 让它重答**
- 单次修复最多 80 轮工具调用（可通过 `PI_FIXER_MAX_TURNS` 环境变量调整）
- 修复报告和代码改动补丁（diff.patch）实时落盘保存

### ⑥ 自动验证（自动）

- 运行该项目配置的验证/测试命令；未配置命令时此环节自动通过（此时修复质量完全依赖 ⑦ 评审把关）

### ⑦ AI 评审（自动，质量闸门）

- 独立的 AI 评审员（Reviewer，**只读权限**，不能改代码）审查：补丁是否真正解决了报告的问题、是否引入回归风险
- 评审不通过（否决 / 高回归风险）→ `REVIEW_REJECTED`，修复不交付

### ⑧ 推送（DRY_RUN=false 时启用）

- 提交修复代码到 `ai/BUG-编号-title` 分支
- 推送到远端仓库
- 安全边界：只允许 `ai/*` 分支，禁止推送 main/master/develop；远端仓库主机必须在 `GIT_ALLOWED_HOSTS` 白名单中
- 推送成功 → `READY_FOR_HUMAN_REVIEW`
- 推送失败 → `PUSH_FAILED`

## 每个状态是什么意思

| 状态 | 含义 | 需要人做什么 |
|---|---|---|
| `COLLECTING` | 对话收集信息中 | 继续对话 |
| `READY_FOR_CONFIRMATION` | 信息已齐全，等待确认 | 确认提交或继续补充 |
| `NEEDS_INFO` | 信息不足，未进队列 | 补充信息 |
| `QUEUED` | 已入队，等待修复 | 无 |
| `PREPARING_ENV` | 准备环境（克隆仓库） | 无 |
| `FIXING` | AI 修复中 | 无，可随时看进度 |
| `FIX_CANDIDATE` | 候选修复已产生，待评估 | 无 |
| `VALIDATING` | 运行验证命令 | 无 |
| `REVIEWING` | AI 评审中 | 无 |
| `FIX_READY` | 修复完成且通过评审（DRY_RUN） | **查看补丁，决定是否采纳** |
| `PUSHING` | 推送中（DRY_RUN=false） | 无 |
| `READY_FOR_HUMAN_REVIEW` | 已推送到 ai/* 分支 | **人工审核合并** |
| `FIX_FAILED` | 修复环节失败 | 查看失败原因，可重试 |
| `ENVIRONMENT_FAILED` | 环境准备失败 | 检查仓库地址/分支 |
| `VALIDATION_FAILED` | 验证命令失败 | 检查验证命令/配置 |
| `REVIEW_REJECTED` | AI 评审否决了修复 | 查看评审意见，可重试 |
| `PUSH_FAILED` | 推送失败 | 检查远端主机白名单/网络 |
| `CANCELLED` | 已取消 | 无 |
| `BLOCKED` | 被阻塞 | 排查阻塞原因 |

## 修复产物（每个 Bug 一套，权限 600）

位置：`data/agent-results/BUG-编号/`

| 文件 | 内容 | 谁看 |
|---|---|---|
| `bug.json` | 结构化 Bug 报告 | 所有人 |
| `fix-task.json` | 交给 AI 的任务书 | 开发 |
| `agent-result.json` | **AI 的修复自述**：根因、改动、信心值 | **所有人（重点）** |
| `diff.patch` | **修复的代码改动补丁（唯一代码成果）** | **开发（重点）** |
| `validation.json` | 自动验证结果 | 开发 |
| `review.json` | AI 评审结论 | 所有人 |
| `git-result.json` | 推送结果（branch、commitSha、pushed） | 开发 |
| `pipeline.json` | 流程时间线与结果 | 排障 |
| `environment-run.json` | 环境准备日志 | 排障 |
| `environment.json` | 环境配置快照 | 排障 |
| `environment-stop.json` | 环境清理记录 | 排障 |

> DRY_RUN=true 时，代码改动**只保存在 diff.patch 中**，不落在任何 git 分支上。采纳修复时：`git apply diff.patch`。
> DRY_RUN=false 时，修复代码已推送到远端 `ai/` 分支，可直接 checkout 查看。

## 配置说明

`.env` 关键项：

| 变量 | 说明 | 默认值 |
|---|---|---|
| `DRY_RUN` | true=只产出补丁不推送；false=推送 | `true` |
| `GIT_ALLOWED_HOSTS` | 允许推送的远端主机白名单，逗号分隔 | `localhost` |
| `PI_SANDBOX_PROFILE` | 必须配置，否则修复 worker 不启动 | — |
| `PI_FIXER_MAX_TURNS` | 修复工程师最大工具调用轮数 | `80` |
| `GIT_HOST` | 推送目标 Git 主机 | `localhost` |

## 常见问题

**Q：AI 修复失败了几次怎么办？**
A：失败原因会记录在 `pipeline.json`，系统会保留失败时的 AI 原始输出和已产生的 diff.patch 供排查。Dashboard 上点"重试"即可重新修复，重试会重建工作区，不会残留脏状态。

**Q：AI 会把代码推到我们的仓库吗？**
A：DRY_RUN=true 时绝不推送。DRY_RUN=false 时只推 `ai/*` 前缀的独立分支，且受保护分支（main/master/develop）禁止推送，远端主机不在白名单会拒绝推送，必须人工审核合并。

**Q：修复质量可靠吗？**
A：三道闸门——① AI 修复员必须输出结构化自述；② 仓库自带验证命令必须通过（如有配置）；③ 独立的 AI 评审员只读复核（可否决）。最终仍需人工审核，系统定位是"自动产出候选修复"，不是"无人值守合并"。

**Q：一个 Bug 要跑多久？**
A：实测约 10-25 分钟，主要耗时在 AI 修复环节阅读代码定位根因。前端项目因代码格式特殊（.ose 文件）可能接近上限。

## 实测案例

### BUG-000004（DRY_RUN=false，推送测试）

- **报告**：store 页面点击 module 分类 tab（App Desktop Addon）无反应，无控制台报错
- **AI 定位根因**：`Title.ose` 组件未声明/渲染 `id` 属性，导致 `CatalogAnchor` 的锚点跳转失效；辅助修复 `CatalogAnchor.ose` 的滚动容器获取逻辑
- **AI 修复**：改动 2 个文件（Title.ose +10/-3，CatalogAnchor.ose +21/-11）
- **AI 评审**：通过（approve），回归风险低
- **推送**：成功推送到远端 `ai/BUG-000004-module-tab`，commit `7bf953f`
- **结果**：`READY_FOR_HUMAN_REVIEW`，全程约 20 分钟

### BUG-000002（DRY_RUN=true，流程验证）

- **报告**：同一类 tab 切换无反应问题
- **AI 定位根因**：页面滚动容器迁移后，CatalogAnchor 的固定层级 parentElement 链失效
- **AI 修复**：改用 `scrollIntoView` 滚动到目标分类
- **AI 评审**：通过（approve）
- **结果**：`FIX_READY`，补丁保存在 diff.patch，未推送
